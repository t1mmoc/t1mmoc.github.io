> 前情：[《两天半，1 个人 + 1 个 AI，我造了一家游戏工作室》](/posts/2026-09-28-ai-game-studio/)——我靠一个 WorkBuddy Agent，两天半做出可联机桌游《烽决》。这篇拆方法论的内核：**怎么把一个 AI 当一支团队使**。

# 一、先纠正一个误区：「一个 AI」不等于「一个员工」

大多数人对 AI 编程的想象是：一个很能干的员工，你下需求，他写代码。这么用，你只能得到一个累死的全栈实习生。

我的用法是：**一个 Agent，多个会话，每个会话绑定一个专家角色**——PM、前端、后端、规则设计师、美术、音效、DevOps。它们不共享对话记忆，但共享同一批 Git 仓库和文档。这支「团队」的组织结构长这样：

```
                你（创意总监 + 终审）
                     │
              WorkBuddy Agent
     ┌────────┬────────┼────────┬─────────┐
   PM 会话   前端会话  后端会话  美术会话  音效会话
     │         │        │        │         │
     └─────────┴────┬───┴────────┴─────────┘
              共享记忆：Git 仓库 + 文档
   （五仓结构 / PRD / 数据清单 / 进度复盘 / 工作日志）
```

关键不是「多开会话」，而是**每个会话只干一类事、只看自己该看的文档**。PM 会话不写代码，前端会话不管部署，美术会话不碰规则。

# 二、五个仓库，就是五个部门的「工位」

团队分工落到文件系统上，是五个 Git 仓库：

| 仓库 | 相当于 | 职责 |
|---|---|---|
| `duelchess` | 前端部 | React 同屏双人 + 在线对战界面 |
| `duelchess_rules` | 规则部 | 纯 TS 规则引擎，74 例单测，不含任何 UI |
| `duelchess_server` | 后端部 | Cloudflare Worker + DO 实时对战 + D1/R2/KV |
| `duelchess_mapbuilder` | 工具部 | 地图编辑器，双层 schema + 预设块 |
| 聚合仓 | 总办 | 子模块指针 + 文档 + 发版 tag |

为什么要拆这么细？因为**仓库边界就是授权边界**。让 AI 改规则引擎时，它物理上碰不到前端代码；发版时聚合仓 bump 子模块指针，五个仓打同一个 tag——这就是「部门汇报」的仪式感，也是回滚的单位。

规则引擎单独成仓还有个隐藏收益：它是纯函数库，单测 74 例全绿就是「规则部 KPI」，任何平衡性调整都有 CI 门禁兜底。

# 三、共享记忆：团队不脑爆，靠文档对齐

多会话最大的坑是**上下文割裂**：前端会话不知道 PM 会话刚定的口径，改着改着就跑偏。我的解法是把「团队记忆」全部外置成文件：

- **PRD**：立项时先让 AI 写一版给我审，之后所有会话按它对齐；
- **进度复盘**：PM 会话定期产出，里程碑状态以代码实查为准，不凭记忆；
- **数据清单**：宣发用的硬数字（130 提交 / 9.5k 行 / 74 单测），统一口径，谁引用谁看这份；
- **工作日志**：每天一档，谁干了什么、踩了什么坑，下个会话先读日志再动手。

这套东西的本质是：**把「开会」变成「读文档」**。AI 会话之间不用同步，它们只需要在同一份事实源上工作。

# 四、重资产并行：worktree 是美术部的「外包车间」

棋子贴图 142 张、音效 30 个（15 类），如果挤在主工作区串行做，主线代码会被美术资源提交淹没。我用 Git worktree 给美术和音效开了**独立工作区**：同一个仓库，物理隔离的目录，各改各的，最后合流。

经验有三条：

1. **资产规格先行**：先在文档里定死尺寸、命名、透明通道，美术会话照规格批量产出，返工率极低；
2. **合流走 git，不走聊天**：美术会话在自己的 worktree 提交，主线合并时冲突极少——因为改的文件本来就不重叠；
3. **AI 产资产要敢于抛弃**：第一批贴图里不协调的直接扔，口头反馈「配色更暗、线条更粗」比精细的 prompt 调参有效。

# 五、插曲：让团队自己玩一局

方法论文讲完了，放个小插曲。为了给规则引擎做压力测试，我让两个 AI 会话在「勇往直前」地图上对打了一局——37 步，红方夺基地获胜。每手棋 AI 都写了决策理由，比如终局前：

> 「攻击 b11——若 b11 是空陷阱则白吃通行，下回合直吃真基地获胜；**若 b11 是真陷阱则同归于尽，但仍暴露 b12 基地供后续进攻**。」

结果是假基地诱饵被识破，3 级白吃通行，直取真基地。这局的完整复盘我单独整理了素材（含一局 743 步的马拉松），以后有机会展开——它证明了两件事：规则引擎扛得住长对局不崩，以及**暗棋类游戏里 AI 的「情报账」算得比想象中细**。

# 六、管理成本没有消失，只是换了形态

必须诚实：AI 团队不是免费的。省掉的是沟通成本、招聘成本、工资；**没省掉的是管理成本**——它全部转移到你身上：

- 口径漂移要你抓（两个会话对游戏定位的表述不一致，我盯着改的）；
- 误判要你纠（PM 会话曾断言「规则引擎没实现传送门」，实查后被打脸——AI 也会想当然）；
- 并行撞车要你仲裁（两个会话同时动前端，一个的 WIP 差点被另一个误提交）；
- 终审永远是你（发布、打 tag、推主干，这些按钮只能你按）。

一句话总结这套方法论：**你从「最累的员工」变成「唯一的瓶颈」**。两天半做一款游戏，靠的不是 AI 有多神，而是你把「管理」这件事本身做成了文档和流程。
