# 这篇讲什么

一个安装包，怎么从「不知道怎么存」做到「能写出它的解包程序」。

不点名任何软件、不说被分析的是哪个包、不放任何未加密的原始文件——样本只以 GPG 加密的形式随仓库发布。留着的只有方法路径、偏移量、结构体字段，以及几个我自己踩过的判断。

# 一、入口不是资源段，是体积

第一反应都是走 PE 资源：安装包嘛，图标、版本信息、对话框都在资源里，内嵌文件大概也在。

打开资源看了，**没有有用信息**。这条路是死的。

真正的入口是一个更笨的线索：**这个 EXE 的体积，明显大于它承载的内容。**一个功能简单的客户端，装它不需要几十兆。资源段里没有，体积又异常，那数据只可能挂在标准结构之后——直接追加在文件尾部。

这个判断不需要任何工具，看一眼属性里的文件大小就够了。但它决定了后面所有动作的方向：既然数据是「贴在可执行体后面的」，那就别在静态结构里找了，**去看程序运行时怎么读自己**。

# 二、让程序自己交代它读了什么

下断点，两个地方：`CreateFileW` 和 `ReadFile`。

关键是**别一上来就单步**。前面那几轮读取全是运行库和配置文件的初始化，硬啃会浪费大量时间，直接快步放行掉。

然后有一条极好用的旁证，是我当时数出来的：

> **每进行 2 次 `ReadFile`，就会多出一个新文件。**

这句话的价值比它看起来大得多。它意味着「读两次 → 产出一个文件」这个配对关系是稳定重复的，也就是说**外层存在一个以文件为单位的循环**，而每次循环内部有两次读取。不用看懂一行代码，光数调用次数就能确认循环的骨架。

顺带一条否定性结论同样值钱：拿 010 Editor 直接搜内嵌文件的明文，**搜不到**。这说明「存进 EXE 的数据」和「文件实际内容」不一致，中间一定有某种变换（压缩或加密）。这条排除掉之后，才不会再往「直接 dump 出来就能用」的方向浪费时间。

# 三、追堆栈找函数，以及「只分析真正跑的那条路」

接下来是断下读取、然后漫长的堆栈回溯，从系统调用一层层爬回业务代码。

这里运气成分不小：**函数名没有被混淆**。所以爬上去之后直接就能读到语义，不需要从寄存器组合反推这个函数在干什么。

爬上去看到的东西也值得说一句。同一个动作存在好几个变体——带云字样的、带 Ex 字样的，名字都很像正主。但**这几个变体一次都没被调用过**。判断依据就是断点根本停不住。

所以只分析真正执行的那两个函数，其余的全部放掉。这个取舍省下的时间比想象中多：不执行的路径你分析得再透，对这个包的还原也没有贡献。

# 四、认出双层循环，字段才开始可猜

两个函数分别对应两层循环，结构一下就清楚了：

- **外层在 install 里，是文件循环**：每循环一次，生成一个文件
- **内层在 extract 里，是数据循环**：每循环一次，给当前文件追加一段数据

![文件循环](/images/installer-reverse-method/2024-04-14-16-44-05-image.png)
![数据循环](/images/installer-reverse-method/2024-04-14-16-43-21-image.png)

到这里，"猜字段含义"这件事才真正开始有着力点。因为循环层数一旦确认，每个循环入口读的那块固定长度的数据就必然是**头部**，而头部里长度不固定的那段大概率是文件名。反过来，如果先不去确认循环结构、直接对着一堆字节猜字段，基本是在猜谜。

然后就是主体工作量本身了，没有什么技巧可言：**猜测、分析、验证、推翻、重新猜测**。找到准确的函数、并且它没被混淆没被加密的时候，最难的部分已经过去了。

# 五、靠数据头猜中压缩方案

每个文件数据前面那个短头部，是判断压缩方案的关键。它的特征指向 LZMA。

验证方式很朴素：拿数据头之后偏移 5 字节的位置作为输入，调 `LzmaUncompress`，能解出正常内容就成立。不成立再换假设。

![解压验证](/images/installer-reverse-method/2024-04-14-18-31-57-image.png)

方案确认之后，剩下的就是把参数复刻、把程序复刻。**前期的寻找最折磨，找到目标点以后写代码反而是简单的那一半。**

# 六、用结构体把格式钉下来

最后落成的格式，用结构体表达：

| 部位 | 长度 / 判据 | 含义 |
|---|---|---|
| 元数据块 | `0x15C8` | 包级头部，紧随基址 |
| 文件头 | `0x194` | 每个文件一条，循环读取 |
| ↳ 名字 | 头部前 `0x190` | 文件（或目录）名 |
| ↳ 时间戳 | `+0x190` | 4 字节 |
| ↳ 是否目录 | `+0xC8` 处取值为 `-1` | 目录标志 |
| 分片数 | 文件头内的计数字段 | 决定内层数据循环跑几轮 |
| 数据头 | `0x8` | 每片数据前的短头 |
| ↳ 有效数据 | 数据头 +5 起 | 喂给 `LzmaUncompress` |
| 文件长度 | 小端存储 | 反着读就对了 |

基址本身有两个值，对应两个不同的样本包。代码里那两行并排的 `#define` 注释就是这件事留下的痕迹——同一套分析在两个样本上各走了一遍，第二个样本的基址变了，其余结构完全一致。

还有一处容易读错的是分隔标记。前后断了四次才收敛，前三次分别错在：程序自身标注的位置、分割区尾部那两个 `00` 被划错了区、以及某个位置只读进来一个字节而且它和解码数据在同一个函数里。**第四次才是真正解码数据的位置。**这种「看起来像边界但其实不是」的地方，靠一次断点是确认不了的。

# 七、验收：跑两遍，比清单

程序写完不算完。我的做法是让它把包内所有文件的元信息全量打出来：基址、数据区起点、每个文件头位置、是否目录、文件名、压缩后长度。

然后在**两个基址上各跑一遍，逐行对齐**。对得上，才说明这套结构不是只对眼前这个样本过拟合。

这一步和"抓完一本书要数文件数"是同一件事：**跑完不等于跑对，得有一个独立于程序自身的判据。**

# 八、一处试手废在哪

同一件事我当时还顺手写了个 python 版，废了。原因值得记：

- 它读那个 `.lzma` 样本，然后调 `zlib.decompress` 去解。**数据是 LZMA，不是 zlib**，方向从第一步就是错的。
- 另一个反向的 `zip()` 函数用了 `lzma.compress`，但整个文件只 `import zlib`，**没导入过 lzma**。也就是说这个函数从来没成功跑过。

结论不客气：**能读通格式，和能写通还原，是两件事。**最后走通的是那份 260 行的 C++，python 那份只是个试手残留，我在仓库里把它原样留着了——留着比删掉有用，它能提醒我别把"我猜是这样"当成"我验过是这样"。

代码、偏移笔记、以及加密后的样本都在这个仓：https://cnb.cool/t1mmoc/tspace/pwngore/h7-installer-unpack

# 收尾

五个可以搬走的东西：

> **体积异常当入口** → **用系统调用断点让程序自报读取行为** → **只分析真正被执行的那条路径** → **先确认循环层数再猜字段** → **用否定性结论（搜不到明文、解不出内容）缩小变换范围**

外加一条纪律：格式复刻完，换第二个样本再跑一遍。只对眼前这个包成立的"格式"，通常只是我把它的字节抄了一遍。
